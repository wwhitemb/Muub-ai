# 飞书嵌入式单片机技术文档写作规则

## 自动调用和协作顺序

- 当用户要求创建、编写、整理或修改飞书文档，且内容涉及嵌入式单片机主题时，先采用本技能的结构和写作规则。
- 需要实际创建或修改飞书云文档时，再叠加 `lark-doc` 技能执行文档操作；本技能负责内容和格式，`lark-doc` 负责飞书文档 API、节点和正文写入。
- 需要浏览知识库目录或参考已有 Wiki 时，叠加 `lark-wiki`；需要读取已有文档正文时，叠加 `lark-doc` 的读取流程。
- 若用户只要求普通通知、行政文档、邮件、审批或非嵌入式内容，不调用本技能。
- 若用户明确指定其他标题格式或公司模板，以用户当前指令为准，并在输出中说明已覆盖的规则。

## 目标和适用范围

将芯片、板卡、裸机、RTOS、驱动、通信协议、存储、功耗、调试和测试信息整理成可检索、可复现、可维护的技术文档。默认使用简体中文；代码、命令、寄存器名、协议字段和工具名称保留其真实拼写。

不得编造芯片参数、寄存器地址、引脚复用、时钟频率、协议 ID、SDK API、构建命令或测试结果。资料不足时使用“待确认”或“待实测”标记，并列出需要补充的证据。

## 标题层级和编号

正文最多使用四级标题。编号必须与标题文字在同一行，编号后保留一个空格。下方 Markdown 模板的 `# 文档标题` 代表飞书文档名称，不计入正文层级；`##`、`###`、`####`、`#####` 分别代表正文的一至四级标题。

1. 一级标题：使用汉字数字加顿号，例如 `一、硬件平台`、`二、软件架构`、`三、验证结果`。
2. 二级标题：使用阿拉伯数字加句点，例如 `1. 芯片与板卡`、`2. 初始化流程`。
3. 三级标题：使用圈数字，例如 `① 时钟来源`、`② 复位条件`、`③ 异常表现`。
4. 四级标题：使用小写罗马数字加右括号，例如 `i）输入条件`、`ii）处理步骤`、`iii）输出结果`。

标题规则：

- 一级标题按 `一、`、`二、`、`三、` 顺序递增；每个一级标题表示一个主要技术板块。
- 二级标题在所属一级标题内从 `1.` 重新开始，便于移动章节后仍保持可读性。
- 三级标题优先使用 `①` 至 `⑳`；超过 20 项时拆分小节或改用列表。
- 四级标题只用于步骤、条件、结果等细分内容，不为了装饰而建立标题。
- 不得跳级，例如不能从 `一、` 直接进入 `①`；标题内容应具体到对象、动作、结论或故障现象。
- 文档名称不强行编号；文档内部一级标题统一使用汉字数字格式。

## 默认文档结构

你的知识库以“学习笔记 + 可复现实验教程”为主。没有特殊要求时，按以下顺序组织；无内容的章节应删除，不保留空标题。

```markdown
# 文档标题

> 摘要：本文说明什么对象、解决什么问题、适用于什么版本。

**文档状态**：草稿 / 评审中 / 已确认 / 已归档
**适用平台**：芯片、开发板、软件版本
**更新时间**：YYYY-MM-DD
**标签**：芯片、模块、接口、文档类型

## 一、平台与目标

### 1. 硬件环境

### 2. 软件环境

### 3. 目标与范围

## 二、原理与配置

### 1. 工作原理

### 2. CubeMX/工程配置

### 3. 代码实现

## 三、下载、现象与验证

### 1. 编译和下载

### 2. 运行现象

### 3. 问题排查

## 四、结论与资料

### 1. 结论

### 2. 待办和未决问题

### 3. 参考资料与变更记录
```

## 技术背景记录

嵌入式文档开头应明确边界，至少按实际情况记录：

- 芯片型号、封装、核心架构和数据手册版本。
- 开发板或产品版本、供电条件、晶振/时钟来源、关键引脚和复用配置。
- 编译器、工具链、SDK、BSP、RTOS、库和提交版本。
- 目标功能、非目标范围、前置条件和已知限制。
- 文档依据：数据手册、参考手册、芯片勘误、原理图、协议文档、逻辑分析仪/示波器记录或测试日志。

缺少具体值时写明“未确认”，不要以常见型号或经验值替代实际参数。

## 教程型笔记规则

针对“配置某外设并验证效果”的笔记，优先采用下面的叙述顺序：

1. 先说明这次实验使用的芯片、开发板、屏幕/存储器/传感器和目标现象。
2. 再说明原理和关键计算，例如总线时钟、分频、采样率、像素时钟、帧缓冲大小或地址映射。
3. 按可执行步骤记录 CubeMX、Keil、IAR、VS Code、SDK 或工程配置；每一步注明配置项、取值、取值依据和影响。
4. 给出需要手写或修改的文件路径、函数名、关键代码及调用位置；生成代码与用户代码分开说明。
5. 编译、下载、复位后记录实际现象，并给出截图、串口日志、波形、寄存器读数或测试文件作为证据。
6. 最后记录问题排查、已知限制、可迁移部分和下一步计划。

每个配置步骤使用“动作 → 参数 → 原因 → 预期结果”格式；截图不能替代文字说明，截图下方必须说明看什么、为什么重要。

推荐的单个实验小节格式：

```markdown
## 一、实验名称

### 1. 实验目标

### 2. 硬件和软件环境

### 3. 原理与关键参数

### 4. 工程配置

#### i）配置项

动作：
参数：
依据：
预期结果：

### 5. 代码实现

### 6. 编译下载与运行现象

### 7. 问题排查

### 8. 结论和参考资料
```

## 参数、图片和代码的表达

- 关键参数优先用表格表达，至少包含“参数名、配置值、单位、来源/计算、影响”。
- 时钟、分频、分辨率、帧率、缓冲区大小、地址和超时必须带单位；计算结果保留公式和代入值。
- 引脚配置记录端口、引脚号、复用功能、上下拉、速度、有效电平和冲突风险。
- 图片按“配置界面、原理图/时序图、代码或日志、最终现象”分类；每张图有简短说明，不连续堆放无说明截图。
- 代码块注明文件名和位置，例如 `main.c / main()`、`ltdc.c / ltdc_draw_point()`；仅展示关键改动，完整工程通过附件或仓库引用。
- 代码注释说明原因、前置条件、边界和失败影响；未经验证的 AI 建议标记为“待验证”，不得写成实测结论。
- 外部链接记录资料名称、来源、版本或章节；链接失效时保留标题和本地证据索引。

## 本知识库主题的专项规则

- STM32/CubeMX/HAL：记录芯片完整型号、CubeMX 版本、HAL 包版本、时钟树、GPIO 复用、NVIC 优先级和生成代码修改点。
- Keil/编译链接：记录 MDK/ARM Compiler 版本、编译选项、MicroLIB、优化等级、下载器、散装加载文件和 Flash/RAM 使用量。
- SDRAM/NOR Flash/SD 卡：记录型号、总线宽度、时序参数、起始地址、容量、初始化顺序、读写验证和 Cache/MPU 影响。
- LTDC/RGB/LVGL：记录分辨率、RGB565/RGB888、像素时钟、HSYNC/VSYNC、前后沿、极性、图层、帧缓冲地址和显存容量计算。
- UART/SPI/I2C/CAN/USB：记录速率、帧格式、DMA/中断方式、缓冲区、分包策略、超时、校验和异常恢复。
- FatFS/LittleFS/文件系统：记录介质、挂载流程、分区、读写路径、掉电风险、格式化条件和错误码。
- Cache/MPU/DMA：明确数据所在存储区、Cache 清理/失效操作、内存属性、DMA 可访问范围和一致性验证。
- 触摸、传感器和外设模块：记录器件型号、地址/片选、初始化寄存器、坐标或数据换算、异常值和校准方法。

## 设计和实现规则

### 架构与模块边界

- 说明应用层、业务层、驱动/HAL、OS 适配层和硬件之间的依赖方向。
- 新模块说明职责、输入、输出、依赖、初始化顺序、资源所有权和失败影响。
- 业务逻辑不得直接操作寄存器；硬件差异集中在驱动或适配层。
- 记录线程、任务、中断、回调和定时器的触发来源、状态变化及退出条件。

### 接口、协议和数据

- 对 UART、SPI、I2C、CAN、USB、RS485、GPIO 等接口记录角色、引脚、速率、模式、帧格式和超时。
- 协议说明应包含字段顺序、字节数、字节序、缩放因子、有效范围、校验方式、错误码和版本兼容性。
- 多字节字段不得只写“按协议解析”；应明确高低字节顺序和位域范围。
- 外部输入、长度、索引、枚举、计数器和物理量必须说明边界校验及异常处理。

### 寄存器和时序

- 记录寄存器名称、地址来源、复位值、关键位域、读写属性和修改影响；地址必须有可追溯依据。
- 用表格或时序图说明初始化先后、建立时间、采样边沿、等待条件、中断清除和超时路径。
- 需要延时或轮询时，记录延时依据、最长等待时间和超时后的降级行为。

### 并发、内存和资源

- 说明中断与任务、多个任务之间共享的数据，以及使用的临界区、互斥锁、信号量、消息队列或原子操作。
- 记录缓冲区容量、生产者/消费者、溢出策略、内存所有权和释放路径。
- 中断中的操作必须符合目标平台的中断安全要求；相关限制写入实现说明。
- 记录任务优先级、栈大小依据、周期/触发方式和资源不足时的表现。

## 代码和示例规则

- 行内代码、宏、类型、函数、变量、文件路径、命令、寄存器和协议字段使用反引号。
- 多行代码使用带语言标识的代码块，并注明用途、调用前置条件、输入、输出和错误路径。
- 示例代码必须与目标平台和 SDK 版本相符；未知 API 使用占位符并标注待确认，不伪造可编译结论。
- 对公共接口、回调、状态切换、资源生命周期、输入校验和错误路径补充中文注释，说明触发来源、状态结果和失败影响。
- 敏感信息、量产密钥、真实账号和设备序列号使用占位符或脱敏值。

## 测试、调试和证据

测试记录至少包含：

| 项目 | 内容 |
| --- | --- |
| 测试环境 | 板卡、芯片、固件、工具链和供电条件 |
| 操作步骤 | 可复现的烧录、配置、输入和观测步骤 |
| 预期结果 | 协议响应、引脚电平、日志、波形或状态变化 |
| 实际结果 | 实测数据和证据位置 |
| 判定 | 通过、失败、部分通过或待确认 |
| 复现条件 | 触发概率、温度、电压、负载和版本条件 |

调试文档应区分“现象、最小复现、假设、排查过程、根因、修复、回归结果”。没有实测证据的内容标记为“推测”或“待验证”。

## 待办、风险和决策

待办使用可执行格式：

```markdown
- [ ] 补充某芯片某外设的实测时序（负责人：姓名；截止：YYYY-MM-DD）
- [x] 完成某版本固件的回归测试（完成：YYYY-MM-DD；证据：日志链接）
```

风险和未决问题使用以下字段：

| 问题或风险 | 影响 | 触发条件 | 临时措施 | 负责人 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 待确认内容 | 对功能/安全/交付的影响 | 如何出现 | 当前规避方式 | 姓名 | 待确认 |

关键技术决策记录“决策、候选方案、选择原因、影响、验证方式、日期和决策人”，避免只留下结论。

## 可检索性和版本维护

- 文档标题包含对象和主题，必要时加入芯片、模块、版本或日期，例如“STM32G4 UART DMA 接收异常排查（V1.2）”。
- 标签控制在 3 至 6 个，优先使用芯片/平台、外设/协议、问题类型和文档类型。
- 日期统一使用 `YYYY-MM-DD`，时间统一使用 `HH:mm`；版本使用项目已有的版本格式。
- 缩写首次出现时给出中文或英文全称，后续保持同一写法。
- 引用外部资料时记录名称、版本、章节/页码和链接；关键参数尽量保留截图、波形、日志或测试文件索引。
- 文档结尾保留“变更记录”，记录日期、变更内容、影响范围和变更人。

## 生成流程

1. 判断文档类型：芯片笔记、驱动说明、接口协议、移植指南、设计方案、调试记录、问题复盘或测试报告。
2. 收集并区分硬件事实、软件配置、设计判断、实测结果、推测和待确认项。
3. 先建立一级和二级标题，再填充三级、四级内容；标题编号遵守本技能的四级格式。
4. 补齐接口、边界、时序、并发、资源、错误路径和验证证据。
5. 对不确定的参数、API、地址、命令和结论标记来源或“待确认”，不得擅自补全。
6. 最后生成结论、风险、待办和变更记录，并执行输出前检查。

## 输出前检查清单

- [ ] 一级标题统一为 `一、...`，二级为 `1. ...`，三级为 `① ...`，四级为 `i）...`。
- [ ] 标题没有跳级、空标题或只为装饰创建的章节。
- [ ] 已写明适用芯片/板卡、软件版本、工具链和文档依据；未知项已标记。
- [ ] 接口或协议包含字段、字节序、边界、校验、超时和错误处理（适用时）。
- [ ] 寄存器、引脚、时钟、时序和 API 均有来源，未编造具体参数。
- [ ] 并发、内存、缓冲区、资源所有权和中断限制已说明（适用时）。
- [ ] 测试记录包含环境、步骤、预期、实测结果、判定和证据位置。
- [ ] 待办包含动作；已知时包含负责人、截止日期和交付物。
- [ ] 事实、判断、推测和待确认项已区分；敏感信息已脱敏。
- [ ] 变更记录、版本、日期、标签和术语已统一。

## 适用边界

本技能规范飞书中嵌入式单片机技术文档的内容组织和排版，不替代具体芯片手册、SDK 规范、代码安全规范、协议标准或测试规程。需要执行飞书权限、审批、任务、日历或数据表操作时，使用对应的飞书技能或工具。
