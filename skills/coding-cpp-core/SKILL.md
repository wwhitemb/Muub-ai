# C/C++ 通用开发规范

## 适用范围

这是所有 C/C++ 代码任务的基础 Skill。它只处理可跨项目复用的规则；嵌入式安全、RT-Thread、Qt、LVGL、协议和业务数据规则由对应 Skill 补充。

## 按需参考

- 新建公共 API、类型、回调、配置宏或模块命名时，加载 `references/cpp-naming-and-api.md`。
- 新建完整 `.h/.c`、`.hpp/.cpp` 文件，或需要完整错误清理骨架时，加载 `references/cpp-module-template.md`。
- 只做局部修改、且目标模块已有明确约定时，不加载上述模板。
- 参考文件中的 `<PROJECT_...>` 和模块名只是占位符，所有单位、范围、返回值和生命周期必须以目标工程证据替换。

## 执行规则

### 1. 命名

- 函数、变量和文件名遵循项目现有风格；没有约定时使用小写下划线。
- 公共符号带模块或领域前缀，避免通用短名称污染命名空间；保持已有公共 API 不变。
- 类型、枚举和宏遵循项目既有后缀/前缀；新增类型优先使用明确的领域名，不使用匈牙利式类型编码。
- 常量、配置项和位掩码使用命名宏或枚举，禁止散落魔法数字。
- 缩写只使用项目已有或行业通用形式；不为局部变量制造难以理解的新缩写。

### 2. 文件与头文件

- 头文件只声明接口、类型和必要常量；实现细节留在源文件。
- 头文件使用项目既有的 include guard 或 `#pragma once`，不混用两种形式。
- include 按“本模块头文件、项目头文件、第三方/系统头文件”分组，并删除未使用依赖。
- 公共 API 的声明、定义和调用方保持签名、所有权、返回值语义一致。
- 新文件或大范围重写时补充简短文件职责说明；局部修改不虚构作者、日期或硬件信息。

### 3. 格式与实现

- 保持项目缩进、括号、换行和命名风格；一次修改不要顺手格式化无关代码。
- 函数保持单一职责；重复逻辑优先复用现有接口，不为一次性代码新增抽象层。
- 输入、外部数据和资源边界先校验；错误返回必须被处理或明确向上传递。
- 资源创建与释放成对出现，所有权和生命周期在接口附近可见。
- 共享状态遵循项目已有同步机制；不跨框架混用锁、事件或线程 API。

### 4. 注释与 API 文档

- 只要响应中包含新增或修改的 C/C++ 代码，默认启用**详细注释模式**；新增或修改的注释默认使用中文，不得批量改写既有英文注释。
- 详细注释模式下，每个新增或修改的函数都必须在函数定义或声明附近补充函数级中文注释：公共 API 使用完整 Doxygen，私有/静态函数至少说明用途、输入、输出、副作用、前提和失败处理。
- 详细注释模式下，新增或修改的宏、文件级/静态变量、局部变量、结构体字段、枚举项、函数参数和资源句柄，都必须有同一行或紧邻的中文说明；参数可用函数 Doxygen 的 `@param` 说明，但不能完全省略。
- 详细注释模式下，新增或修改的状态赋值、模式切换、资源申请/释放、条件分支、循环、早返回、边界检查、空指针判断、并发保护和错误路径，都必须在代码附近说明原因、触发条件、结果和失败影响。
- 注释解释“为什么”、边界和约束，不只翻译标识符或复述显而易见的语法；无法确认的单位、范围或平台行为必须标记“待项目确认”。
- 用户明确要求“简洁注释”“简要注释”或同义表述时，切换为简洁注释模式：保留函数注释、声明注释和关键风险点注释，但采用一句话说明，不扩展详细背景。
- 用户明确要求“不生成注释”“省略注释”或“仅输出无注释代码”时，才关闭注释；用户说“只给代码”不等于关闭注释。
- Doxygen 用于公共接口以及项目已采用的函数文档位置；详细模式下新增或修改的私有/静态函数也必须有函数级注释，但不要求为未修改的历史函数补注释。

## 交付前检查

1. 公共 API、调用方和错误返回是否兼容。
2. 新增命名是否符合当前模块约定，是否引入魔法数字或无依据缩写。
3. 默认详细模式下，本次新增或修改的每个函数、声明、状态赋值、资源操作、分支和错误路径是否都有邻近中文注释。
4. 用户要求简洁注释时，是否仍保留函数、声明和关键风险点注释且没有扩展为无关长文。
5. 只检查本次 diff 的格式、注释语言和无关变更；不因默认详细模式批量改写未修改的历史注释。
